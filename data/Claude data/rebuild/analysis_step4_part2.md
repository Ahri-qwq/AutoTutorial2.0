def extract_key_paragraphs(self, chapter_content):
    # 提取包含关键词的段落
    keywords = ["参数", "设置", "INPUT", "STRU", "示例", "代码"]
    paragraphs = chapter_content.split("\n\n")

    key_paragraphs = []
    for para in paragraphs:
        if any(kw in para for kw in keywords):
            key_paragraphs.append(para)
            if len("\n\n".join(key_paragraphs)) > 300:
                break

    return "\n\n".join(key_paragraphs)
```

**优势：**
- 不需要额外的LLM调用
- 提取的内容更有针对性

## 7. 信息丢失分析

### 7.1 章节详细内容丢失
**现象：**
- 每章只保留前300字符的摘要
- 详细内容（如完整代码示例）丢失

**是否合理：** ✅ 合理

**理由：**
1. Step 4的任务是撰写前言和附录，不需要章节详细内容
2. 章节详细内容已经在最终文档中（通过文件拼接）
3. 如果传递完整章节内容，会导致上下文爆炸

**验证：**
- 最终文档包含完整的章节内容
- 前言和附录不需要引用章节的具体代码

---

### 7.2 检索结果的原始文档丢失
**现象：**
- 背景知识检索到6个文档
- 这些文档的原始内容不会保留到最终输出

**是否合理：** ✅ 合理

**理由：**
1. 检索结果只是用于生成前言和附录
2. 最终文档不需要包含检索结果的原始内容
3. 用户关心的是教程内容，而非检索过程

---

### 7.3 中间步骤的元信息丢失
**现象：**
- Step 1的特殊指令不会出现在最终文档中
- Step 2的大纲设计思路不会出现在最终文档中

**是否合理：** ✅ 合理

**理由：**
1. 这些元信息是给系统内部使用的
2. 用户不需要看到系统的内部工作流程
3. 最终文档应该是"干净"的教程，不包含元信息

**潜在需求：**
- 有些用户可能想了解教程的生成过程
- 可以提供"调试模式"，输出完整的中间文件

## 8. 上下文过长来源分析

### 8.1 上下文组成
**Step 4的LLM输入：**
```
1. 提示词模板: ~1000 tokens
2. 章节摘要 (5章×300字符): ~2000 tokens
3. 背景知识检索 (6个文档): ~6000 tokens
────────────────────────────────
总计: 9000 tokens
```

**上下文过长的主要来源：**
1. **背景知识检索**（占67%）
   - 6个文档，每个约900字符
   - 可能包含冗余信息

2. **章节摘要**（占22%）
   - 5章×300字符
   - 已经是压缩后的内容

3. **提示词模板**（占11%）
   - 当前模板已经比较精简

---

### 8.2 是否是历史对话累积？
**答案：** ❌ 不是

**验证：**
- Step 4的LLM调用是独立的
- 不包含前面步骤的对话历史
- 只包含当前步骤的输入

**关键区别：**
```
❌ 错误理解：
Step 1-3的LLM对话 → Step 4的LLM对话（累积）

✅ 正确理解：
Step 1-3的输出文件 → Step 4的输入（文件内容）
```

---

**上下文长度对比：**
| 步骤 | 上下文长度 | 主要来源 |

### 12.1 四步流程的协同
```

| **任务性质** | 内容生成 | 内容组装 |
